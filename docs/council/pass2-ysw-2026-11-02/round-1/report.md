## Blocking issues

- **[sol] B1** (Recommended exact spec diff; §§10/12.3 mixed-fat-object applicability; contract): The proposal changes launch-estimate and certificate invocation contracts without stating how a mixed fat object uses them. INDEX's general assertion that no north-star capability is removed does not supply the module boundary, launch-shim responsibility or certificate inventory required by the standing mixed-fat-object check. This is an omission in the proposed repair, not a request to redesign the accepted launch ABI. *Fix:* Add this paragraph to the recommended normative diff for §§10/12.3: “In a mixed fat object, native host code remains native. The host launch shim loads the selected marked ISA module and negotiates the token-alias binding feature with its runtime and scheduler. Execution derives token_aliases from the actual live handles supplied to that device invocation; tuple-based estimate and scheduling requests supply the partition explicitly. Alias-bearing schedules and certificate invocation records bind the selected module's object/closure identities and resolved device invocation, rather than treating the native host binary as one ISA object. Native entry points, argv/envp and unaffected host libc require no device token-alias entries; the alias-binding inventory covers the marked device closures and their invocations.”
- **[codex] B1** (Recommended exact spec diff: partition ordering and no-token defaults; §§10.1/11/12.3; contract): *Fix:* In §§10.1/11/12.3 and both no-token defaults, state: “For an oracle invocation, list its separate invocation token first, followed by token-typed arguments in signature order. For an action, permutation action or CC/R entry, list only token-typed parameters in signature order. Budget fields do not create token identities. The separate budget token accepted by the estimation ABI contributes an identity slot only when the subject is an oracle.” Correct examples: a token-free oracle has [0]; token-free controlled and flip actions have []; an action receiving a,b has [0,0] for one shared identity and [0,1] for distinct identities. Alternatively, define an explicit action context-token mechanism and its runtime propagation, but I recommend omitting the nonexistent primary identity because this preserves §4.7 and source hashes.

- **[codex] B2** (Release and route; mixed-fat-object standing check; contract): The proposal changes launch support, invocation identity and certificate bindings, but neither it nor INDEX's publication section states how a native-host-plus-marked-device-modules fat object uses them. The general assertion that no North Star capability is removed does not supply the explicit mixed-object application required by the standing check. *Fix:* Add to Release and route: “A mixed fat object retains its native host binary and carries ISA objects and device certificates for marked device modules and their linked device closure. These token partitions are scoped to invocations of a loaded device program, not to the whole native binary. The launch runtime derives entry partitions from valid device token handles and preserves equality through device calls; serialization records equality classes only. Native host-only functions need no device certificate, and this repair does not require moving host entry points, argv/envp or the native libc closure into an ISA object.”

## sol

The identity gap is real and the partition repair is sound. The cited clause numbers, fixture pin and catalog/hash premises check out, including INDEX's conditional publication caveat. Revise only for the mandatory mixed-fat-object applicability statement.

**Path to accept:** Add B1's mixed-fat-object applicability paragraph to the proposed normative diff. No other blocking change is required.

- **C1 5**: The partition preserves the token ledger and token lifetimes in §§3.2/5.4. Local labels encode equality without becoming runtime handles. *Change:* Optional §3.2 cross-reference: “The token equality relation exported in an invocation binding is encoded by token_aliases (§12.3).”
- **C2 5**: No instruction changes. Fresh budget.mint identities and forwarding agree with §§4.1/4.7/5.4. *Change:* Optional §4.1 budget.mint annotation: “Serializing token_aliases neither mints a token nor changes its validity.”
- **C3 5**: The cited identity distinction is real: §5.3 requires identical identities and tuples; §§4.1/7.4 compare boundary values. Preserving mappings through captures and inverse traversal repairs the distinction without inspecting quantum data. *Change:* Optional §7.4 frame clarification: “Region-call history retains the resolved token identity context in addition to token tuples for inverse traversal.”
- **C4 5**: Including the partition in schedule matching preserves §10.1's selected-realisation accounting. The proposal leaves target resources, exact rational aggregation and outward decimal encoding unchanged. *Change:* Optional §10.1 clarification: “Exact resource aggregation uses the realization selected by args, budget and token_aliases together.”
- **C5 4**: The proposal covers invocation bindings, schedule/cache matching, inverse-pair coverage and universal claims. Additive ABI symbols avoid an in-place signature change. The mandatory mixed-fat-object applicability statement is missing. *Change:* Add to §§10/12.3: “In a mixed fat object, token_aliases binds invocations of the selected marked ISA module and its device closure; it does not make the native host binary a device object.”
- **C6 4**: The source fixture validates with the reported object hash cda0f55ff3f299b165453ff9162b051ddf96856a799d22e09499c226bf35c011. The hand-derived four-step success and third-step fault are consistent with §7.4. INDEX's partition checks are correct, but its step assertions are not an independent execution check, as the note acknowledges. *Change:* Add to §15: “For a memoryless identity oracle and two consecutive action-body oracle_call occurrences on the same wires using equal-tuple arguments a and b, partitions [0,1,1] and [0,1,2] respectively produce one K65 carrier at the second call and no carrier, with the separately supplied primary token distinct from both arguments.”
- **C7 4**: Every consistent alias partition remains representable, preserving north-star scope. However, neither ysw nor INDEX's publication section explains the mixed fat object's use of the changed launch/certificate contract; the standing check explicitly makes that silence blocking. *Change:* Add to the exact diff: “Native host entry points, argv/envp and unaffected host libc remain outside the device token-alias inventory; only marked device closures and their invocations require these bindings.”
- **C8 4**: Canonical ordering, tuple consistency, nested identity mappings and catalog boundaries are implementable. The old ABI's optional uniform-result route would benefit from a concrete default. *Change:* Add to §10.1: “The legacy estimate function defaults to E_ARG when token arguments require an unavailable alias binding; callers obtain an exact estimate for each consistent partition through bennett_estimate_run_with_token_aliases.”

Suggestions:
1. §10.1, legacy ABI paragraph: state “Absent an explicitly defined uniform-result certificate form, a legacy estimate request with token arguments and no alias binding returns E_ARG; the alias-aware function supports every consistent partition.” Alternatively define a certificate form quantified over all consistent partitions now. I would use the E_ARG default for the legacy entry point and retain exact coverage through the new entry point.
2. §15 and Conformance vectors: add a concrete Q witness. Use a memoryless oracle with body “lift.retval x” and an action containing “oracle_call @identity a (x) t f () (); oracle_call @identity b (x) t f () ()”. With a distinct primary token and all tuples equal, [0,1,1] must give a sole K65 carrier at the second call; [0,1,2] must give none. Both contexts remain valid. For the published CC witness, both args arrays hash to bf8eae8d885943f1948223391b24a677ec8eaefc4d39544bd6ed106277a211ed.

## codex

The identity defect is real and the canonical-partition repair is sound in principle. Revise the false generalization that every region has a primary token, and explicitly preserve mixed-fat-object use. Tuple hashes and catalog-preservation claims check out subject to the stated publication route.

**Path to accept:** 1. Define action partitions without an invented primary identity and update the ABI defaults and examples accordingly. 2. Add the explicit mixed-fat-object application paragraph. These are the two acceptance blockers; the remaining recommendations are discretionary.

- **C1 5**: The equality partition preserves §5.4 fresh-token semantics without exposing process-local identifiers. Forwarding and dynamic mint occurrences retain distinct meanings. *Change:* No required change. Retain the proposed rule: “A successful mint creates a fresh identity attached to that dynamic defining occurrence.”
- **C2 5**: No opcode or instruction signature needs changing. The CC uncall witness agrees with §§4.1/7.4; its four-versus-three forward source-step counts are correctly identified as derivations. *Change:* In Recommended exact spec diff, state: “This repair changes invocation metadata, not the operand lists of oracle_call, action_call, call or uncall.”
- **C3 5**: §5.3 explicitly requires token identities and tuples for matching. Preserving identities through captures and inverse traversal repairs the relevant K81 distinction without replacing identity equality by tuple equality. *Change:* In Conformance vectors, add: “Reversing a mint revokes that occurrence’s token; a subsequent mint of the same tuple produces a distinct identity and does not revive the revoked token.”
- **C4 4**: Comparing aliases alongside params_hash closes the demonstrated scheduling ambiguity. However, the partition rule presupposes a primary token for actions, whose source calls have none. *Change:* In §§10.1/11, state: “Action and permutation-action partitions contain only their token-typed arguments; an estimator’s separately supplied budget token contributes no identity slot for an action.”
- **C5 3**: The additive ABI and separate source-binding metadata are appropriate. Action partition formation and the required mixed-fat-object application remain unresolved. K24 and K77 are accurately described. *Change:* In §§11/12.3, replace the blanket region rule with: “Only oracle invocations prepend their separate invocation-token identity; actions, permutation actions and CC/R entries list token parameters alone.”
- **C6 4**: The INDEX partition checks pass. The debug reference CLI admits the originating fixture and reproduces object hash cda0f55ff3f299b165453ff9162b051ddf96856a799d22e09499c226bf35c011. The arithmetic checks do not execute token-sensitive CC or K81 behavior, which the note correctly discloses. *Change:* In Conformance vectors, specify an action containing two successive calls to the one-row identity oracle through token arguments a and b, both at tuple (1,0,0,0): “Both invocations compose to identity; equal handles produce a K65 carrier at the second call, while distinct handles produce no matched-call carrier.”
- **C7 4**: Every consistent alias pattern remains representable, and conditional bounds are not presented as completing exact estimation. However, neither this note nor the shared INDEX explains application to the mixed fat object required by the standing check. *Change:* Add to Release and route: “In a mixed fat object, token partitions bind device invocations of the linked marked modules; native host-only code remains native and does not become part of the device certificate inventory.”
- **C8 4**: Canonical labels, validation, nesting and hash boundaries are mostly clear. The old-ABI paragraph would benefit from a concrete default distinguishing an exact K12 result from a bound across partitions. *Change:* In the ABI paragraph, state: “The default legacy behavior for requests containing token arguments without an explicit partition is E_ARG; callers obtain exact results through the new entry point. A bound across partitions is not a K12 exact estimate.”

Suggestions:
1. ABI compatibility paragraph: adopt the explicit default “A legacy request with token arguments and no partition returns E_ARG; the new entry point supports every consistent partition.” If retaining uniform legacy results, state instead: “A K12 result returned through the legacy ABI must be exact for every consistent partition and carry an explicitly universal binding; a worst-case bound must use a separately identified result kind.” I recommend the first route for this repair.
2. Hashes, catalog and consumers: add “Changing launch/sched/cert versions in an object header changes object_hash even when symbol envelopes remain unchanged; regenerate object bindings and downstream certificate pins. Under an authorized feature-only repair with unchanged header/source bytes, object and symbol hashes remain unchanged, while modified schedule hashes and certificate bytes must be regenerated.” The independently recomputed ref catalog envelope remains 5de4e4995350313e50217880ba1b95de39cd043283b726337d4894efb005d197.
3. Inverse-pair conformance: add “An entry with primary budget (2,0,0,0), argument-token tuple (2,0,0,0) and partition [0,0] does not cover primary budget (3,0,0,0) with that unchanged argument tuple: [0,0] is tuple-inconsistent, while [0,1] changes the certified partition.” This makes the proposed preservation of equality constraints under budget coverage directly testable.
