## Blocking issues

- **[sol] 4ta-B1** (Recommended exact spec diff; interaction with §§3.3 and 4.7; core): Changing B5 alone does not make the illustrated heterogeneous slot consistently usable through the accepted machine interface. §3.3 defines a register as 'n device-resident wires of one class' and records its class in the ledger; §4.7 requires qreg operands for CC/R wire and region slots. Consider a = qreg.new A 1; b = qreg.new B 1; t = qreg.concat a b; action_call @split (t) () () (). Both allocations fit the witness target, and concat meets every printed precondition, but its required result [A,B] contradicts the single-class register definition. The fragment descriptor cannot resolve that contradiction. The note's placement citations are correct, but its claim that this B5-only repair suffices overlooks this interacting clause. *Fix:* Extend the exact diff to §3.3: 'A register denotes an ordered sequence of device wires and records each wire's resolved target class. qreg.new cls n and bennett_qreg_new allocate homogeneous sequences of cls. qreg.concat concatenates the wire and class sequences without moving, copying or reallocating wires; qreg.slice selects corresponding subsequences. Reversal restores the prior sequences and identities. Binding to a region slot requires equality with that slot's expanded B5 class vector and, where present, its inherited topology vertices.' The witness concatenates [A] and [B] into [A,B], returns 3 from initial 0, and reversal restores the original clean registers. Alternatively retain homogeneous base registers and explicitly define composite qreg handles with these concatenation, slicing and binding rules; I recommend the ordered class-vector definition.
- **[sol] 4ta-B2** (Recommended exact spec diff; Hashes, catalog and consumers; contract): This proposal changes certificate layout, but neither its exact diff nor the shared INDEX publication decisions states how a mixed fat object uses that layout. The standing bennett-4ht check explicitly requires that statement. General claims that North Star scope remains unchanged do not identify the device certificate inventory or preserve the native-host boundary. *Fix:* Append to §9.4: 'A mixed fat object retains its native host executable and embeds ISA objects only for marked device modules and their device callee closures. B5 descriptors describe those device invocations and bind to their existing object, closure and schedule identities; the device-region certificate inventory does not require entries for every native host function. At the host/device boundary, existing register ids identify operands whose ordered class vectors must match the selected frames. Host-native functions and host process state do not become ISA frame slots.' No new fat-container encoding or launch entry point is required by this repair.
- **[codex] B1** (Recommended exact spec diff; ISA §3.3 interacting with §§9.4 and 10; core): The proposed heterogeneous frame is not reconciled with the runtime register model. §3.3 explicitly defines a register as “n device-resident wires of one class” and records its singular class. Yet qreg.concat requires only distinct live non-view registers and preserves their wires without movement. On the witness target, allocate qA with one A wire and qB with one B wire, concatenate them, and bind the result to split's wire[2] slot. The concatenation satisfies its stated preconditions and produces the proposed [A,B] placement, but violates the unchanged register definition. Rejecting it, relabelling a bit, and preserving the heterogeneous result cannot all implement the same amended machine. This is a direct interaction with the new class-vector contract, not a denial of the placement-level B5 defect. *Fix:* Extend the diff to §3.3: “A register contains an ordered vector of device-resident wires with a resolved class per wire. A single class abbreviates a homogeneous vector. qreg.new retains its requested-class allocation rule. qreg.concat accepts differing operand classes and concatenates their wire/class vectors without movement; qreg.slice inherits the selected sub-vectors. Free and reversal records preserve and restore the complete vector. Region binding preserves that vector, which the selected §9.4 frame must describe.” Add the A/B concatenation witness: the joined register has classes [A,B], split maps 0,1,2,3 to 3,2,1,0, and reversal restores the original wire ordering, classes and handle states. A separately specified heterogeneous register/view mechanism is another viable route; extending the existing qreg model is the smaller repair.
- **[codex] B2** (Hashes, catalog and consumers; Recommended exact spec diff; contract): The proposal changes certificate layout but contains no mixed-fat-object application statement. INDEX's general assertion that North Star capabilities remain does not state which embedded objects receive these frames or how native host code reaches the fragmented device slot. This fails the council's explicit standing check for certificate-layout changes. *Fix:* Append to §9.4: “In a mixed fat object, these descriptors apply to device-region invocations in the embedded ISA objects, using the certificate's existing object, closure and invocation bindings. Native host modules remain native and require neither ISA conversion nor B5 frame records. Native host code launches a device CC entry through §10; that entry may concatenate homogeneous registers under §3.3 and bind the resulting ordered class vector to one source interface slot. The slot's fragments describe that binding without splitting its signature. Native process entry, argv/environment and host-library execution remain outside this device-frame inventory.” For the witness, the native host launches a device CC wrapper that joins A[1] and B[1] and invokes split with the single mut:0 slot.

## sol

The fragment encoding, worked arithmetic and conditional hash claims are sound. Revision is required for the interacting single-class register rule and the missing mixed-fat-object statement.

**Path to accept:** 1. Reconcile heterogeneous slot binding with §3.3's register definition, concatenation, slicing and reversal using the rule in 4ta-B1. 2. Add the mixed-fat-object applicability and certificate-inventory statement in 4ta-B2. The fragment encoding itself can then be accepted on the authorized 0.9 K route.

- **C1 4**: The fragment intervals preserve wire identity, ordering and ownership. However, the proposed heterogeneous slot interacts with §3.3's explicit definition of a qreg as wires 'of one class'. *Change:* In §3.3 state: 'A register records an ordered wire sequence and each wire's resolved target class; homogeneous allocation requests remain homogeneous.'
- **C2 4**: No quantum instruction changes are required. The class semantics of qreg.concat and qreg.slice nevertheless need reconciliation with the newly representable interface. *Change:* In §3.3 state: 'qreg.concat concatenates the operand wire and class sequences without movement; qreg.slice selects the corresponding subsequences.' Thus [A] concatenated with [B] produces [A,B].
- **C3 5**: Fragments describe placement without adding allocation, aliasing or quantum operations. X on both bits implements t XOR 3, and the adjoint restores every input. Eight read-only reference action executions confirmed these values. *Change:* None required; retain §5.3's unitary and adjoint semantics.
- **C4 4**: The citations to §§8.3 and 11 are accurate. Under sequential timing, §8.2 gives time 2, occupancy 2 per class and peak 1 per class. The fragment rules correctly preserve capacities and topology constraints. *Change:* In §9.4 state: 'At a CC/R region call, the expanded slot-class vector MUST equal the actual operand register's ordered class vector; topology placement additionally preserves those wires' vertices.'
- **C5 4**: The B5 alternative is precise and retains legacy homogeneous records. Under INDEX.md's authorized in-version route, §9.2 excludes certificates from object identity, so the source-hash claim holds. The mixed-fat-object applicability statement is missing. *Change:* In §9.4 state: 'For a mixed fat object, these descriptors cover device invocations of marked ISA modules and their device callees, bound to their existing object, closure and schedule identities.'
- **C6 4**: The finite outputs, region flattening and resource arithmetic check out. The published FRAME hash and 219-recipe catalog envelope hash also match. INDEX.md correctly disclaims implementation of the proposed verifier. *Change:* In 'Conformance vectors' add: 'Allocate one A wire and one B wire, concatenate them, call split through CC/R, require result 3 from initial 0, and reverse to both original clean registers with their original classes and identities.'
- **C7 3**: Preserving heterogeneous placement supports North Star §§4.1–4.4. However, the operational register restriction remains unresolved, and neither the note nor INDEX.md states how the changed certificate layout applies to the mixed native/device fat object required by bennett-4ht. *Change:* Add to the proposed §9.4 text: 'A mixed fat object retains its native host executable; only marked device modules and their device callee closures require ISA frames. Host-native functions and process state do not become frame slots.'
- **C8 4**: Canonical maximal runs, exact coverage, integer encoding and rejection rules are readily implementable. Publication is appropriately conditional in INDEX.md, but consumer migration could be stated more concretely. *Change:* In 'Release and route' state: 'After authorization, updated consumers accept both legacy homogeneous records and fragmented records; consumers lacking this repair reject fragments under the existing unknown-field rule, and producers require an updated consumer before emitting them.'

Suggestions:
1. Conformance vectors: state that the controlled case uses an enlarged target with vertices 0:A, 1:B, 2:C, capacity 1 each, edges [[0,2],[1,2]], and matching exact controlled-X leaves of duration 1. With control c at vertex 2, the expected map is (c,t) -> (c,t XOR (3*c)); sequential time is 2, occupancy is 2 and peak is 1 in each class. The control remains outside mut:0.
2. Conformance vectors: give the region[1,2] case sufficient capacity, for example vertices with classes [A,B,A,B] and capacities 2 each. State: 'mem:0 has width 4; offsets 0,1,2,3 denote cell0.bit0, cell0.bit1, cell1.bit0, cell1.bit1 respectively.' Its four alternating width-one fragments are canonical.
3. Release and route: add the explicit consumer migration sentence given under C8. Retain INDEX.md's distinction: unchanged source hashes depend on an authorized in-version repair; a full-version publication must regenerate affected version-prefixed envelopes and consumer pins.

## codex

The B5 defect, fragment encoding, arithmetic and conditional hash claims are sound. Two interacting omissions prevent acceptance: the homogeneous runtime-register definition and the mandatory mixed-fat-object application statement.

**Path to accept:** First reconcile §3.3's register/class and reversal rules with heterogeneous vectors and add the concatenation witness. Then add the explicit mixed-fat-object application statement. The fragment encoding itself can remain as proposed.

- **C1 4**: The fragment model preserves wire identity and ordering, but its heterogeneous interface vector is not reconciled with §3.3's definition of a register as wires of one class. *Change:* In §3.3 state: “A register contains an ordered wire vector with a resolved class per wire; a single class abbreviates a homogeneous vector.”
- **C2 4**: The X witness is correct and no gate semantics change. The interacting qreg.concat rule permits distinct live operands without requiring equal classes, while the register definition remains homogeneous. *Change:* In §3.3 state: “qreg.concat concatenates the operands' wire and class vectors without moving wires; qreg.slice selects the corresponding sub-vectors.”
- **C3 5**: Fragments introduce no quantum operation, alias, allocation or lifetime. The exact X sequence maps 0,1,2,3 to 3,2,1,0, and its adjoint restores every input. *Change:* No correction required. Optionally add to §9.4: “Fragmentation is descriptive metadata and introduces no gate, measurement or routing operation.”
- **C4 5**: §§8.2–8.4 and §11 support the stated sequential time 2, occupancy 2 per class and peak 1 per class. The proposed topology equality, complete partition and no-double-charge rules are precise. *Change:* No correction required. To strengthen the example, add under Conformance: “For region[1,2], offsets 0,1,2,3 denote (cell,bit) pairs (0,0),(0,1),(1,0),(1,1).”
- **C5 4**: The B5 defect is real: §9.4 supplies one class per complete slot, while §11 supplies per-bit placements. The proposed alternatives and validation rules repair that encoding. The required mixed-fat-object application statement is absent. *Change:* Append to §9.4: “In a mixed fat object, B5 frames describe device-region invocations in embedded ISA objects; native host modules require neither B5 frames nor ISA conversion.”
- **C6 4**: I reproduced the INDEX finite-check prefix and independently checked the basis map, inverse, resource totals and region flattening. The note accurately distinguishes arithmetic checks from unexecuted schema/target validation. Its additional controlled case needs a larger target. *Change:* In Conformance specify a third control vertex of class C, capacity 1, edges to both target vertices and exact controlled-X support; expected output is t for control 0 and t XOR 3 for control 1.
- **C7 4**: The proposal preserves source slots and permits target-driven heterogeneous placement without manufacturing capacity. However, neither the note nor INDEX states how this certificate extension is used by the native-host-plus-device mixed fat object required by the standing check. *Change:* Add the mixed-fat-object rule in B2, including device CC launch and the register binding that makes the fragmented slot reachable.
- **C8 4**: The fragment rules are implementable and retain the homogeneous shorthand. Under INDEX's authorized in-version route, §9.2 excludes certificates from object identity; recipes and ordinals are untouched. I also reproduced the published frame, topology-target and reference-catalog hashes. Consumer migration could be stated more directly. *Change:* In Release and route state: “For the authorized in-version K publication, consumers upgrade to accept both B5 alternatives; older consumers reject fragments under §9.1, and producers must not disguise heterogeneous slots as homogeneous records.”

Suggestions:
1. Conformance vectors: state that the controlled positive case uses vertices 0:A, 1:B, 2:C, capacity 1 each, edges [0,2] and [1,2], and exact controlled-X entries of duration 1. With sequential execution and unit rates, time is 2, each class has occupancy 2 and peak 1; the control is preserved and t maps to t XOR (3·control). The original two-vertex target has no room for the extra control.
2. Release and route / INDEX publication rules: explicitly select the recommended authorized in-version K route and state: “Existing homogeneous certificates retain their encoding; updated consumers accept fragments; older consumers reject the unknown field. Consumers must upgrade before processing fragmented certificates. Source, schedule, target and ref@0.9 bytes remain unchanged when only the certificate descriptor changes.” A full-version publication remains viable, but must instead regenerate affected envelopes and consumer pins as INDEX explains.
