## Blocking issues

- **[sol] LPE-1** (Recommended exact spec diff: extent bindings; ISA §§3.3, 4.7, 5.1 and 16.2; contract): The diff reads extent parameters from "the caller's resolved region descriptor", but CC/R region calls have no such descriptor. Sections 3.3 and 4.7 pass a qreg and validate its total width against an already known region[A,W]; the ledger contains width, not A and W. Thus the presumed descriptor is not an existing call input. An eight-wire actual can represent region[1,4] or region[2,2]. Those shapes differ operationally: XORing integer 1 into cell 1 of an initially zero register produces flattened value 16 or 4 respectively. The proposed bind metadata identifies which axes to read but supplies neither axis at this boundary. Adding width_args to downstream bindings does not define how this source call supplies them. *Fix:* Extend §§4.7, 5.1 and 16.2 with an explicit classical call-shape vector, which I recommend: "Each CC/R family call supplies width_args in header parameter order, separately from ordinary args. A wire-bound entry MUST equal the actual operand's ledger width. Memory-axis entries supply A and W; after substitution, every memory actual MUST have exactly 2^A·W wires and satisfy the existing role and disjointness rules. All values are fixed before coherent entry; a mismatch raises FAULT_UB_TRAP before any effect. Nested coherent calls forward shapes from resolved caller declarations." Alternatively introduce typed region(q,A,W) actuals and read the axes from those; that also works but adds a new operand form. The eight-wire example must distinguish width_args ["1","4"] from ["2","2"], yielding 16 versus 4 for the cell-1 operation. Scheduling and estimation requests without register operands must supply the corresponding complete vector explicitly.
- **[sol] LPE-2** (Recommended exact spec diff: instance bindings; ISA §§9.4, 12.1–12.3; contract): Adding width_args and instance_hash to certificate bindings does not repair the existing certificate record keys. Section 12.3 still permits one regions[closure_hash] record containing one signature and mandatory frame; §9.4 requires literal interface widths after instantiation and permits only c as a frame-expression variable. A fixed root action can invoke the same xor_width family at n=1 and n=3. Both children have the same family closure hash, but their slot widths must respectively be [1,1,4] and [3,3,4]. One existing record cannot satisfy both. The diff neither provides multiple instance records nor defines how claim subjects and inverse-pair references select them. This prevents a conforming certificate for the composed program, despite each instance being individually valid. *Fix:* Extend §§9.4 and 12.1–12.3, not only the root bindings. Recommended rule: "A concrete width-family certificate region record is keyed by instance_hash and carries closure_hash and width_args. Its signature, bounds, frame and domains are resolved for that instance. Claim subjects, inverse-pair references and composition references distinguish instances; verification for one instance MUST NOT discharge another. A parameter-uniform structural claim may cover multiple widths only by explicitly quantifying them and checking its side conditions throughout that domain." Alternatively retain the family closure key and nest records under instances[instance_hash]; either layout works, but choose one normatively. The mixed-width root must contain two child records with widths [1,1,4] and [3,3,4], and an n=1 claim must not certify n=3.
- **[codex] B1** (Recommended exact spec diff, extent bindings; ISA §§3.3, 4.7, 5.1 and 16.2; contract): The diff binds A/W from 'the caller's resolved region descriptor', but that source does not exist at the specified CC/R entry boundary. §4.7 supplies memory slots using qreg operands; §3.3 records a register's total width, not an A/W shape. Existing binding obtains the shape from the literal callee signature. For example, six wires can fill either region[0,6] or region[1,3] in an action. When both dimensions are parameters bound from mem:0, neither the qreg nor the proposed call syntax selects between those shapes. K26 explicitly distinguishes them and forbids inferring shape from total width. The proposal therefore assumes existing entry metadata that the cited contract does not provide. *Fix:* Amend §§3.3, 4.7, 5.1 and 16.2: 'At a CC/R call, a memory actual whose A or W is parameterised carries an explicit descriptor (q,A,W), with A and W classical unsigned-i64 values or literals. Before any effect, including view consumption, require A≥0, W≥1 and width(q)=2^A·W using mathematical integer arithmetic, then bind the declared extent parameters from that descriptor. Failure is FAULT_UB_TRAP. Coherent callers forward the resolved descriptor of their interface or local region; no shape is inferred from total width.' Thus a six-wire q with (A,W)=(0,6) and the same q with (1,3) select distinct instance bindings. Alternatively, bind extents from explicitly designated classical argument slots and perform the same checks. I recommend the explicit call descriptor, which preserves the separation from ordinary args.
- **[codex] B2** (Recommended exact spec diff, instance bindings; ISA §§9.4, 11.1 and 12.1–12.3; contract): Adding width_args and instance_hash to certificate bindings does not resolve the existing certificate representation. §12.3 has exactly one region record per closure_hash, containing one signature and mandatory frame. §9.4 requires slot widths to match the signature and permits only inherited-control count c as a frame-expression variable. Consider outer[n,m] invoking the same family flip[k] on two mutable bundles, forwarding n and m respectively; flip's body is x v[0], valid at every positive width. At n=1,m=3 and c=0, both callees have the same family closure_hash but require mut:0 frame widths 1 and 3. One closure-keyed record cannot represent both, and a single root instance binding cannot identify both child instances. This prevents a conformant composed certificate or launch estimate for a legal use of the extension. *Fix:* Amend §§9.4 and 12.1–12.3: 'A family region record contains instance records indexed by instance_hash. Each instance record carries width_args, the substituted signature and bounds, and its concrete frame and verification records. Every concrete executable claim and inverse-pair reference identifies the relevant instance. Nested invocation contexts resolve and retain each callee's own width_args and instance_hash; composition distinguishes instance identity in addition to family closure, variant and inherited controls. A width-uniform structural claim must explicitly quantify over all covered admissible width vectors.' In §11.1 require shape context to survive argument/body/template capture and forwarding, as invocation-token context does. The witness must produce two child records, with slot widths 1 and 3 and one forward occurrence each. Alternatively, extend frame/signature expressions and claim quantification to support symbolic family-wide records; I recommend separate concrete instance records as the smaller repair.

## sol

The expressiveness diagnosis, XOR witnesses and frozen-0.9 catalog claims are correct. Classical width specialization preserves the accepted core semantics. Two contract blockers remain: CC/R extent descriptors are presumed but unavailable, and certificates cannot represent multiple shapes under one family closure key.

**Path to accept:** First define the classical extent-binding channel and its pre-effect checks (LPE-1). Then define instance-specific certificate records and references, including a mixed-width root example (LPE-2). With those changes I would accept the proposed 0.10 extension; the note expressly proposes no normative 0.9 K repair.

- **C1 4**: Classical resolution before coherent entry preserves the existing fixed-shape machine. However, §§3.3 and 4.7 supply qreg operands at CC/R calls, not the region descriptors presumed by the new extent bindings. *Change:* In §5.1 state: "Every extent parameter is supplied through an explicit classical call-shape binding and validated against the actual register before any effect."
- **C2 4**: Literal substitution preserves existing instruction semantics. The proposed source rules explicitly cover wire[n] and loop/allocation bounds but do not enumerate parameter occurrences in reg widths, region types or width-bearing opcode suffixes. *Change:* In §16.2 state: "The permitted parameter occurrences are explicitly listed size positions; all other integer positions remain literal, and substitution precedes ordinary operand validation." Publish that list with the grammar.
- **C3 5**: Fixing widths classically and applying the existing invariants after substitution introduces no quantum-dependent sizing. Both XOR examples are correct; exhaustive arithmetic checks passed for all 64 n=1 tuples and 1024 n=3 tuples. *Change:* Optional clarification in §5.1: "A resolved family's denotation is exactly that of its literal substitution; control and adjoint preserve that same width binding."
- **C4 4**: Instance-sensitive cache keys and resolved integer catalog descriptors are appropriate. The existing scheduler and §10.1 estimator requests lack a separate width vector, while the proposal correctly forbids putting widths silently into ordinary args. *Change:* In §§10.1 and 11 state: "A standalone family scheduling or estimation request supplies the complete ordered width_args vector; its instance_hash is recomputed and validated before expansion."
- **C5 3**: Family versus instance identity is a sound distinction, but extent binding lacks an input channel and the closure-keyed certificate schema cannot represent different concrete frames for multiple instances of one family. *Change:* Extend §§9.4 and 12.3 with the instance-keyed certificate rule in LPE-2, including resolved signatures, frames and claim subjects.
- **C6 4**: The verification script passes and accurately checks the hand XOR values, without claiming consumer execution. The proposed conformance cases are useful but omit a single root containing two different widths of the same family. *Change:* Add to conformance: "One root invokes xor_width at n=1 and n=3 with empty ordinary args; both instances must coexist in its certificate with interface widths [1,1,4] and [3,3,4]."
- **C7 5**: The cited ISA and dialect premises check out, including dialect §8.4, §24 D34 and §25.3 G-17. The note correctly distinguishes existing denotational expressiveness from practical emission and preserves the full valid domain. *Change:* In the dialect append replace "classical but not statically finite" with "classical but not statically enumerated"; unsigned-i64 shape domains are finite.
- **C8 3**: The proposal gives a useful compact design and a responsible 0.10 release boundary. The advertised exact diff still leaves two normative contract decisions unresolved. *Change:* In the instantiation paragraph state: "Resolve explicit call-shape inputs, derive instance identity, substitute source sizes, validate the concrete region, and only then construct executable, schedule and certificate records."

Suggestions:
1. Identity, §9.2: state "The instance-hash preimage uses the family's 64 lowercase ASCII hexadecimal closure-hash characters, followed by LF; width_args is the header-ordered JCS array of canonical unsigned decimal strings, followed by LF." Publish a byte-exact vector so consumers cannot choose raw digest bytes instead.
2. Grammar, §16.2: state "Substitution is capture-free and applies only to declared size positions; parameter names are resolved in a separate width namespace." Include reg widths, region axes and any supported width-bearing opcode suffixes explicitly; unsupported expression forms remain outside this extension.
3. Release and hashes: state "This proposal changes the 0.10 contract only. Every symbol re-emitted with isa=0.10 is rehashed under §9.2, including symbols without width parameters; published 0.9 objects and ref@0.9 remain unchanged." Publish the affected launch/sched/cert version selections and the 0.10 expansion-library default together. The current 219-recipe catalog check reproduces hash 5de4e4995350313e50217880ba1b95de39cd043283b726337d4894efb005d197.
4. Conformance: add "A false width_args/instance_hash pair rejects before replay; two different qreg ids with identical shape share instance identity; a single root may contain different instances of the same family." Preserve the existing n=1 result (1,1,0), n=3 result (5,6,0), and K79 address-only () rule.

## codex

The existing-width premises, XOR examples and frozen-catalog claim check out. The proposed 0.10 direction is sound, but entry extent binding assumes unavailable metadata, and composed certificates cannot represent multiple widths of one family. Both are contract blockers.

**Path to accept:** 1. Supply the explicit CC/R extent-binding mechanism in B1. 2. Define instance-specific certificate/frame composition and nested shape-context preservation as in B2, with the two-width witness. Retain the proposed 0.10 release boundary. No change to the underlying quantum machine is required.

- **C1 5**: The proposed substitution occurs before coherent entry and preserves §3.1's classical-control invariant. Each resolved instance retains the existing machine model. *Change:* §5.1: state, 'A resolved family instance denotes the ordinary region obtained by capture-free substitution; its widths remain fixed throughout that invocation and its reversal.'
- **C2 4**: The existing instruction semantics suffice after substitution. The proposal explicitly admits wire[n] and loop/allocation parameters but does not enumerate corresponding body-width occurrences in §16.2. *Change:* §16.2: state, 'Bound width parameters may occur in wire[N], reg[N], region[A,W], lifted width suffixes, allocation dimensions, and qloop/bounds counts; each occurrence becomes a literal before ordinary validation. No arithmetic expression or loop index is introduced implicitly.'
- **C3 5**: The identity-oracle examples agree with §5.2: 0 XOR 1 = 1 and 3 XOR 5 = 6. Exhaustive arithmetic checks covered arbitrary targets and four-bit fault values at n=1 and n=3, with both control values. K79 correctly permits () for A=0 without admitting wire[0]. *Change:* §5.2: state, 'For every admissible width vector, the existing full-domain oracle, control, adjoint, prefix-reversal and workspace-restoration obligations apply independently to the resolved instance.'
- **C4 4**: Including instance_hash in schedule/cache bindings prevents cross-width reuse. The executor-resource reference is real: §17 item 16 distinguishes executor exhaustion from the oracle's reference outcome. Estimate and scheduler request transport remains to be specified. *Change:* §10.1 and §11: state, 'A family estimate or scheduling request supplies the complete resolved width_args independently of ordinary args; the consumer validates those values and derives instance_hash before expansion, without requiring live register ids.'
- **C5 3**: Two contract conflicts remain: CC/R supplies qreg operands rather than the proposed source region descriptors; and §12.3's closure-keyed certificate records cannot represent different concrete frames for two widths of one family. *Change:* §4.7 and §5.1: state, 'A CC/R memory actual with parameterised extents supplies an explicit classical shape descriptor; its dimensions bind the extent parameters only after the register-width and disjointness checks succeed.' Apply B1's complete rule.
- **C6 4**: Specialisation preserves the existing theorem hypotheses. Verification claims are appropriately limited to arithmetic, but the proposed vectors do not exercise two widths of the same callee within one certificate; B2 prevents an unambiguous checker implementation. *Change:* §12.3: state, 'Concrete signatures, frames and executable claims are indexed by resolved instance identity; proof or evidence for one width vector does not cover another unless the claim explicitly quantifies over both.'
- **C7 5**: The cited ISA §3.3, dialect §8.4, D34 and G-17 support the note's classification as an efficiency/interface extension. Retaining the full valid domain and prohibiting cache misses from becoming invalid-width faults respects the north star. *Change:* Dialect §8.4: replace 'classical but not statically finite' with 'classical but not finitely enumerated by the compiler's value analysis'; the representable unsigned-i64 domain is already finite.
- **C8 3**: The note clearly separates existing expressiveness from practical emission and recommends an honest 0.10 boundary. Its exact-diff section omits consequential changes to call binding, frames and certificate composition. *Change:* Recommended exact spec diff: state, 'This 0.10 extension also amends §§3.3, 4.7, 9.4, 10.1 and 12.1–12.3 with explicit entry-shape binding and instance-specific certificate composition; it does not modify published 0.9 objects.'

Suggestions:
1. §9.2: make the instance-hash bytes explicit: 'Hash UTF-8("width-instance\n" + lowercase-64-hex-family-closure + "\n" + JCS(width_args) + "\n"); width_args contains canonical unsigned decimal strings in header order, without leading zeros except "0".' For the synthetic family hash consisting of 64 zeroes, ["1"] hashes to 3486e3dc5d4e3a80a35d4338f5ff126b787ded89baaee9f66aca083e7025cf6e and ["3"] to 9ae5c34acce5452f6c24f31e97baa9ddfc027a44c609a5e77f4eb54759feacd3.
2. Hashes, catalog and consumers / §17 item 7: state an explicit 0.10 expansion default. One viable rule is, 'Resolved instances use the unchanged ref@0.9 catalog, with expansion hash 5de4e4995350313e50217880ba1b95de39cd043283b726337d4894efb005d197, unless another library is explicitly bound.' I verified that hash against the 219-recipe file. Alternatively publish ref@0.10 with a new versioned envelope and hash. I recommend explicit reuse if its operation definitions remain unchanged; the current default otherwise asks for ref at the object's ISA version.
3. §15 / Conformance vectors: add the concrete memoryless family body 'lift.retval x'. State, 'At B≥1 it maps (x,t,f) to (x,t XOR x,f); at B=0 it maps to (x,t,f XOR 1). A false outer control leaves the entire tuple unchanged.' Exercise these outcomes at n=1 and n=3, and include B2's two-width composed certificate.
4. §5.1: clarify the family validity obligation: 'A supported family must instantiate to a well-formed region at every shape admitted by its signature. A body that becomes ill-formed at an admitted shape is an invalid family, not evidence that the caller supplied an invalid width.' This separates producer validity from cache availability without requiring a particular proof algorithm.
5. Release and after acceptance: state, 'This is a 0.10 extension, not authorization to apply incompatible bytes as a 0.9 K repair. Changed schedule and certificate interchange formats receive explicit versions; unchanged 0.9 objects and catalog bytes retain their identities.'
