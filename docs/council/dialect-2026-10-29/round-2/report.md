## Blocking issues

- **[sol] SOL-R2-01** (§10 TDL-9/TDL-7; §18.3–§18.4; core/S0): TDL-9 says exhaustion "stops the generation ... no further source instruction executes", but §18.4 requires for ctrl/adj that "every register allocated during the generation is freed during it", otherwise T-LEAK. Witness: an action body executes `%h = call ptr @__bennett_qalloc(i64 0, i64 1); call void @__bennett_gate(i32 1, ptr %h, i64 0); call void @__bennett_gate(i32 1, ptr %h, i64 0); call void @__bennett_qfree(ptr %h); ret void`. With one G step it records qalloc, exhausts before the first gate, and never reaches qfree. Literal leak checking traps with code 4 during generation, even when the outer control is 0; TDL-9 instead promises code 1 under that control. Suppressing the trap alone leaves an unmatched allocation. This is an interaction introduced by the D02-08 fix, not a demand for a cleanup proof. *Fix:* State in TDL-9 and §18.4: "Generation exhaustion is an invocation failure, not a source leak. Compiler finalization runs after exhaustion without consuming the exhausted generation budget. By default, abort before applying recorded events: discard the invocation's speculative views and recorders, cancel its invocation-owned provisional allocations, preserve foreign handles, and emit only the appropriate fault event under its invocation/path controls. Failed compute generation does not execute use; failure of either part cancels the still-unapplied composite invocation. Normal T-LEAK checking applies to a successfully completed source generation." Alternatively preserve the prefix with an explicit reversible cleanup of every local allocation/workspace; I would cancel the recorder because §18.4 records before application. Add the witness: no local h remains live, foreign registers are unchanged, control=0 gives Φ=0, control=1 gives Φ=1, and neither branch traps T-LEAK/T-CLEAN.
- **[sol] SOL-R2-02** (§8.5 empty-R optimization and snapshot reuse; §16.2 prologue; core/S0): §8.5 promises a "private copy of the caller's whole classical memory" and says replay makes heap_used/atop equal caller entry values, but omits transfer when the load read-set R is empty. Allocation state affects results without loading caller bytes. Use §16.9's normative malloc body, just __bennett_nz_alloc: a CC caller has already allocated 16 bytes at heap_base=4096, then invokes an oracle containing malloc(16), ptrtoint and return, with no alloca or other memory load. R is empty and no stack-use addition applies. The prescribed fresh wrapper returns 4096; private caller-state execution returns 4112. Both succeed with sufficient budget. Independently checked/hashed ISA probes through the supplied interpreter via stdin confirmed payloads 4096 versus 4112, code 0. Snapshot reuse also invalidates only on "store to an object of R"; allocation/free changes k, bump or live bits without such a store. *Fix:* State in §8.5: "Entry-state dependencies include allocation history/liveness metadata whenever the closure may allocate, free, validate caller storage or observe an allocation-derived address. Replay k, sizes and live bits in these cases even when the byte read-set is empty; include bytes only as required by byte dependencies. Omit replay only when both byte and allocator-state dependencies are absent. Invalidate cached snapshots on relevant alloc/free and shadow-stack push/pop/restore operations as well as stores." Apply this decision in §16.2 before private allocations. The witness returns 4112, code 0, preserving caller state; after another caller allocation of 16 bytes, the next invocation returns 4128. Replaying full allocation history for allocation-sensitive closures is the sound default; a smaller proven dependency is optional.
- **[sol] SOL-R2-03** (§12.6 N21; §16.1 completeness; core/S0): §12.6 includes "casts" among elementwise instructions, but LLVM bitcast can change lane count/width or cross scalar/vector boundaries. No other N21 row handles that case. Little-endian witness: `%v = load <2 x i32>, ptr %p, align 1; %b = bitcast <2 x i32> %v to <4 x i16>; %r = extractelement <4 x i16> %b, i32 1; ret i16 %r`, with bytes 44 33 22 11 88 77 66 55. Correct result is 0x1122 (4386). An elementwise i32-to-i16 bitcast is illegal and cannot produce four lanes; retaining the vector violates V13/§16.1. LLVM 18 and 23 verify and fold the equivalent constant-pattern probe to `ret i16 4386`. The missing expansion also leaves canonical row counts, hence F_B, undefined for an accepted construct. *Fix:* Add to §12.6: "Bitcast is elementwise only when source and destination lane geometries agree. Otherwise form the source packed bit string in datalayout order and resegment it into destination lanes or a scalar. On supported little-endian targets, lane 0 occupies the low bits. The default expansion zero-extends source carriers to total width, shifts by cumulative widths and ORs in increasing source-lane order; extracts destination lanes by logical right shift and truncation in increasing destination-lane order, omitting identity casts and zero shifts. N22 legalises total widths above 128. Legalization drops no source memory access." Add scalar↔vector and lane-changing pairs. For the witness retain both i32 loads at offsets 0/4 and return trunc.i16(lshr.i32(first_load,16))=4386, code 0. Rejecting the cast would narrow scope.
- **[sol] SOL-R2-04** (§12.6 N21 blanket llvm.vp.* rule; Appendix C; core/S0): The blanket VP rule defines active as k<evl and mask[k], with inactive lanes yielding 0 except masked-load passthrough. That is false for VP selection: false-condition lanes have defined values. Witness: `%v = call <2 x i32> @llvm.vp.merge.v2i32(<2 x i1> <i1 true,i1 false>, <2 x i32> <i32 5,i32 6>, <2 x i32> <i32 7,i32 9>, i32 2); %r = extractelement <2 x i32> %v, i32 1`. The blanket rule gives 0; LLVM gives 9. LLVM 18/23 verify the module; LLVM 23 native lowering independently emits `movl $9, %eax; retq`. Installed LLVM 23 VPIntrinsics.def explicitly says vp.select/vp.merge do not report their condition as a predication mask because false lanes have defined results. Appendix C promises both names. *Fix:* State in §12.6: "The generic inactive-zero rule applies only where the intrinsic's LangRef result is poison. For vp.select/vp.merge the condition is a selector, not an inactivity mask: within explicit vector length lower each lane to select(condition[k], on_true[k], on_false[k]). Preserve each intrinsic's specified behavior outside that length and replace only poison by N7 zero; vp.merge preserves its on_false value outside the selected active prefix as well." Give these rules precedence over the generic bullet. Add the witness as a normalisation/native pair returning 9, plus an analogous vp.select false-condition witness. Also state: "VP reductions fold the start value with active lanes only, in increasing lane order; inactive lanes contribute no zero unless zero is that reduction's identity." This prevents the blanket rule from zeroing masked products/AND reductions.
- **[codex] R2-CODEX-01** (§10 TDL-4; §16.3–§16.4; §16.11 arena-o1; §17.1; core/S0): §17.1 requires every access to lie wholly in one live allocation. TDL-4 puts distinct globals and coherent heap objects into one arena, while §16.3 removes their individual global entries and §16.4 checks only the ISA allocation containing the address. ISA §7.2 gives the whole coh interface region one pinned live entry. Thus logical object bounds and liveness disappear. Use the arena-o1 layout with two distinct one-byte globals at offsets 0 and 1, containing 01 and 02. A slice performing load i16 at offset 0 must fault 7: neither global contains both bytes. The specified boundscheck/load rows instead succeed with 513. I reproduced this by adapting arena-o1 in an anonymous memory file, updating its hashes, and running the supplied interpreter: check accepted; run-oracle with coh=0102, arg=0 and budget=100,0,32,1 returned code=0, payload=513, steps=7. Arena padding and freed coherent allocations have the same missing validation. This is a dialect-to-ISA mapping defect, not an ISA gap. *Fix:* In TDL-4 and §16.4 state: "The arena interface range is storage, not a logical allocation. Maintain the base, size and live state of each arena object. Before every program-memory access of n bytes at p, require that the entire nonwrapping range [p,p+n) lies in one live logical allocation; otherwise produce fault 7 before the access. The pinned coh entry does not satisfy this logical check." Use an ordinary materialised runtime helper over this metadata as the default, with its rows charged in the reference object; apply the same validation to event-producing stores and gate their mutation on success. Include coherent allocator allocation/free updates and metadata transfer in the contract. Retain one physical coh region so superposed addressing remains available. Correct witness: the spanning i16 load gives payload=0/code=7, whereas either separate i8 load succeeds with 1 or 2.
- **[codex] R2-CODEX-02** (§8.5 entry-state selection and caching; §16.2 prologue; core/S0): §8.5 promises a private copy of the caller's whole memory and allocator state, but R is still selected from objects the closure may load; "if R is empty, no transfer runs". Allocation primitives read hidden allocator state without an LLVM load. Consider a caller that has allocated 16 bytes at heap_base=4096 and then invokes a materialised oracle consisting only of p=__bennett_nz_alloc(1); return ptrtoint(p). It has no load, global or shadow-stack use, so R is empty and its reference object starts with heap_used=0. It returns 4096; the promised call-entry-state execution returns 4112. With heap budget 16, the inherited-state execution must instead fault 2, while the fresh-heap map succeeds. The stack-adoption fix does not cover this allocation-only closure. Reusing a snapshot solely because no store to R occurred can also miss intervening alloc/free operations. *Fix:* In §8.5 state: "Allocation, deallocation and allocation-validity checks read allocator metadata even when the closure contains no LLVM load. Treat that metadata as an entry-state dependency. Replay the caller's allocation history and live bits whenever those operations can execute, independently of the byte read set; an empty byte read set does not permit resetting allocator state. Snapshot reuse requires unchanged dependent allocation metadata as well as unchanged dependent bytes." Default to replaying the complete allocation table for any closure with such a dependency; bytes may still be omitted when unread. Add the allocation-only witness: after the caller's 16-byte allocation, sufficient-budget payload=4112/code=0, and heap budget 16 gives payload=0/code=2. Neither oracle invocation changes the caller's allocation state.
- **[codex] R2-CODEX-03** (§10 TDL-2 View; §18.4 nested generation; core/S0): The compute-specific recorder fix leaves ordinary nested generations inconsistent. TDL-2 checks enclosing recorders for Co writes, but a Cl byte is still "the shadow updated by the recorder's own classical events". Parent events have not been applied while the parent recorder is active (§18.2). Witness: t starts Cl(0); outer f stores 9 to t and calls ctrl(c2,g), where g flips target z iff t==9; invoke f under c1, with both controls equal to 1 and z=0. The child has no own write to t, K(t) is still Cl, and the parent's unpredicated xmask is not a Co write. The literal child view reads shadow 0, so it omits the flip. The sequential branch semantics promised by TDL-2/§18.4 reads the parent's 9 and flips z. The new retained-recorder sentence applies to compute, not this nested ctrl. *Fix:* Replace the Cl-view sentence in TDL-2 with: "A child generation inherits the invoking generation's current speculative view. A Cl byte is obtained by applying the visible enclosing recorders' classical updates in execution order, then the child's own updates, to the invocation-entry shadow. The enclosing invocation control is not added to that inherited view until event composition. Co writes remain Co, and sibling branch recorders remain isolated until the join."
