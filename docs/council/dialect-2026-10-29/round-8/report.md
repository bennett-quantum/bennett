## Blocking issues

- **[sol] SOL-R8-01** (§5.2 PT3/PT4 and the definition of 'copies'; §3.4 width dispatch; consistency with §12.6 and §18.1; core/S0): PT3 includes 'bitcast' in the rule 'copies (union)', and §5.2 defines copies as 'AV(result) ⊇ AV(operand) lane by lane'. This is false for a bitcast that changes lane geometry. Witness (implicit marker declarations as permitted by §1.5):

target datalayout = "e-p:64:64"
define void @top() {
  %v0 = insertelement <2 x i8> zeroinitializer, i8 1, i32 0
  %v1 = insertelement <2 x i8> %v0, i8 1, i32 1
  %bits = bitcast <2 x i8> %v1 to i16
  %n = zext i16 %bits to i64
  %h = call ptr @__bennett_qalloc(i64 0, i64 %n)
  call void @__bennett_gate(i32 1, ptr %h, i64 256)
  call void @__bennett_gate(i32 1, ptr %h, i64 256)
  call void @__bennett_qfree(ptr %h)
  ret void
}

On the supported little-endian layout, packing the two bytes gives 1 | (1 << 8) = 257. §12.6 emits exactly that packing, then zext preserves 257. The invocation allocates 257 wires, flips wire 256 twice and frees cleanly. LLVM 18 and 23 verify and retain the full witness under default<O0>; instcombine on both folds the allocation operand to 257. Independent native marker harnesses on both majors, for both O0 and instcombine forms, report width=257, gates=2, frees=1, final bit=0 and exit 0. The supplied recogniser instead accepts the O0 witness with AV(bits) and AV(n) containing separate lane-0/lane-1 INT(1) entries and VS(n)={1}. Its normaliser independently emits the correct packed value 257. §3.4 therefore compiles only the width-1 alternative for a materialised width-257 execution. A missing dispatch alternative or allocating one wire and trapping on index 256 violates §18.7. This is a pre-existing PT3 transfer defect, not a regression of the repaired PT10 or PT4 rules. *Fix:* In §5.2 remove bitcast from PT3's unconditional lane-copy list and insert this rule:

'PT3 bitcast: A scalar-to-scalar bitcast of equal representation width, or a vector bitcast with equal lane count and equal per-lane representation widths, copies corresponding bit-pattern domains. Every other bitcast uses the DataLayout bit-string packing and resegmentation of §12.6 during S2, before candidate sets, shapes and dispatch domains freeze. Form each source bit string from the represented source-lane bit patterns in DataLayout order, then extract each destination lane or scalar at its destination representation width. For finite integer lane domains, take the Cartesian product of the source domains, pack and extract each result, and apply K to the resulting destination INT sets. Never copy a source-lane INT atom as the value of a packed destination scalar. If a non-handle destination bit-pattern domain cannot be represented by these rules, use non-handle top for that destination; preserve explicit ROOT provenance and apply §6.2's existing restrictions on handle representations. Apply the same rule to constant expressions. This may be implemented by analysing a virtual §12.6 expansion without requiring LLVM optimisation.'

PT4 then applies the actual zext to the packed scalar domain. Add the full witness to DB/DN/DS: verdict=accept; AV(bits)={INT(257)} as one i16 scalar domain, VS(n)={257}; allocated width=257; two successful X gates at index 256; clean free; fault code 0. Verify source, materialised output and instcombine form on LLVM 18/23, and execute a native marker harness that checks the received width and gate index. Add a scalar-to-vector or different-vector-geometry witness to prevent the inverse transfer from remaining a lane-copy rule. A fixed top fallback for all geometry-changing non-handle bitcasts would be sound numerically but would unnecessarily turn this finite width case into BLK-1; use the precise finite packing rule.

- **[codex] R8-CODEX-02** (§5.2 definition of Copies and PT3/PT4/PT5; §12.6 N21 bitcast packing; §3.4 width dispatch; core/S0): Section 5.2 defines "Copies" as "AV(result) ⊇ AV(operand) lane by lane" and PT3 includes bitcast in "copies (union)". target datalayout = "e-p:64:64-i64:64-n8:16:32:64"
declare ptr @__bennett_qalloc(i64, i64)
declare void @__bennett_qfree(ptr)
define void @top() {
  %a = insertelement <2 x i8> zeroinitializer, i8 1, i32 1
  %b = bitcast <2 x i8> %a to i16

Here %a is <0,1>. Under the specified little-endian packing, %b=0|(1<<8)=256 and %width=256. Copying source lane values can supply only 0 and 1; it cannot supply 256. The N21 output uses zext/shl/or, and native executions of that materialised output with clang 18/23 at O0/O3 all record one width-256 allocation, clean free and exit 0. PT5's generic instruction to evaluate integer casts elementwise does not resolve the explicit conflicting lane-copy rule or specify how source lanes combine. *Fix:* In §5.2 remove bitcast from the unconditional-copy list in PT3 and add this rule to that row: "A bitcast copies lane by lane only when source and destination have identical lane counts and lane bit widths, treating a scalar as one lane. Otherwise use the virtual N21 bitcast expansion of §12.6: pack the source lane bit patterns into its prescribed bit string, then split that string into destination lanes. Compute the output abstract values through the PT4/PT5 transfers of that expansion; finite INT lane sets denote their full Cartesian product, and the K cap applies to each resulting lane. Unknown bits propagate non-handle top through those transfers. Explicit object and ROOT provenance follows the same expansion and remains subject to §6.2; top never substitutes for ROOT. Apply this rule also to constant expressions and the fixed-vscale form, during S2 before verdicts, candidate sets and dispatch domains freeze." Retain N21's execution semantics. Add the full witness to DB/DN/DS with AV(%b)=AV(%width)={INT(256)}, VS(%width)={256}, verdict=accept, and exactly one width-256 allocation followed by clean free/code 0 on LLVM 18 and 23. Add the inverse scalar-to-vector packing probe as a companion. Direct finite bit-string evaluation is an equivalent implementation of this transfer; I recommend the virtual N21 expansion so analysis and execution share the already decided packing rule. Do not classify this finite, valid case as BLK-1 or reject geometry-changing bitcasts.
