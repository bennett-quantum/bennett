## Blocking issues

- **[sol] SOL-R6-01** (§9.2 budget-table identity matching; §7.3 oracle identity; §16.2 wrapper prologue; §19.9 resolved build record; contract/S0): §9.2 says “An entry matches a region by its identity (§7.3, the interface hash of @ref of one shape)” and “For each component a region takes, in order of precedence, the first entry matching by identity”. That includes sstack. §16.2 then emits the shadow-stack setup with “c = lift.const.i64 <sstack>”. This makes the selector depend on the value it selects, and no provisional identity, staging rule or other default breaks the cycle. Witness: use the supported O0 pipeline on `define i8 @f(i8 %x) { %p = alloca [24 x i8], align 8
 store i8 %x, ptr %p, align 1
 %v = load i8, ptr %p, align 1
 ret i8 %v
 }`, an IN(8,zext)/tgt=8 shape, a fixed runtime/link layout and adequate other budgets. LLVM 18 and 23 both verify it and retain the alloca/load under default<O0>. Let H16 and H32 be the interface hashes of its canonical reference objects using sstack=16 and 32 respectively, with all other inputs and raw-table maxima fixed. Use table `{"version":"0.2","defaults":{"steps":"1048576","heap":"1048576","stack":"65536","depth":"256","sstack":"16"},"entries":[{"identity":"H16","sstack":"32"}]}`, substituting the actual H16 digest. If the final object is H16, the entry matches and requires sstack=32, changing the object to H32. If it is H32, the entry does not match and requires the default 16. Thus the literal final-identity rule has no fixed point; a one-pass implementation and a rematching implementation cannot follow one common specified construction. This is semantic configuration, not a field-format omission: with initially unset stack state and helpers needing no additional shadow frames on this path, 16 cannot admit f’s 24-byte frame, whereas 32 can. Independently, hashing the existing entry-stack microvector through bennett-isa-ref hash /dev/stdin confirms the hash dependence: its original init-size constant 16 gives ref hash 50289e34598400f57c820d819d83993e14d12e08596ba55ce070109b5746ad1f; changing only that wrapper constant to 32 gives 100b604880ad883157e645eb234be2edfb5897d851f73321d554915b8d14509c. This microvector probe establishes hash sensitivity, not a claim that it is f’s canonical object. *Fix:* Replace the identity-matching/precedence paragraph of §9.2 with this ordered rule, and cross-reference it from §7.3, §16.2 and §19.9: “Budget-table resolution is staged and does not seek a fixed point. First resolve baseline values for every region and component using the first matching region_key entry, then the first matching symbol entry, then the defaults, ignoring identity entries. Freeze the link’s layout capacities using the componentwise maxima of all defaults, table entries and statically supplied budget records, whether an entry matches or not; later lookup does not shrink or recompute those capacities. Construct each shape’s provisional reference object under that layout using its baseline sstack and other baseline wrapper inputs. Its interface hash is selection_identity. For each component, overlay the first identity entry naming that component whose identity equals selection_identity, or retain the baseline value if none matches. Apply this overlay once only. Generate the final reference object using the resolved values; its interface hash remains the semantic identity of §7.3. Do not re-evaluate identity selectors against that final hash. Record selection_identity, final semantic identity and resolved components in the build record and resolved budget table.” Existing explicit marker-record/table-sentinel precedence remains in force. Add the witness above to DD/DM: an entry keyed by H16 selects 32 exactly once, the final wrapper contains the size constant 32 and has H32, and its build record retains selection_identity=H16. Also test that changing only steps preserves the final object hash while changing the selected token. Another viable repair is a separately defined content hash of the pre-budget closure/shape with symbolic wrapper/layout inputs, used solely for budget lookup; specify its canonical construction and keep final ISA identity separate. I recommend the staged provisional-object rule because it reuses ISA hashing, preserves identity-based configuration and requires no new hash encoding. Removing identity selectors or silently ignoring identity-selected sstack would lose the advertised capability and is not the proposed repair.

- **[codex] R6-CODEX-03** (§12.2 N9; §12.4 V6; §16.1 completeness; core/S0): N9 maps atomicrmw op to "%nz.v.r = <op> T %nz.l.r, v" and enumerates exceptions for xchg, min/max, FP and the round-5 wrap/subtract operations, but omits nand.
