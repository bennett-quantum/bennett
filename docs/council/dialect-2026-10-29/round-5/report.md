## Blocking issues

- **[sol] SOL-R5-01** (1.5 pw; 16.2–16.4 pointer carriers and ptrtoint/inttoptr rows; 17.4 CC/R lowering; 18.1 C state; core/S0): Section 1.5 defines pw from address space 0. Section 16.3 then gives "ptr → pw", and section 16.4 maps ptrtoint/inttoptr with "M = pw: v = lift.mov A". These rules do not account for a different representation width in another address space. Witness under target triple x86_64-unknown-linux-gnu and datalayout "e-p:64:64-p270:32:32-p271:32:32-p272:64:64": define i64 @f(i64 %x) { %p = inttoptr i64 %x to ptr addrspace(270); %r = ptrtoint ptr addrspace(270) %p to i64; ret i64 %r }. At x=4294967296, LLVM truncates to the 32-bit pointer and zero-extends back, yielding 0. The specified pw=64 map emits two 64-bit moves and yields 4294967296. LLVM 18 and 23 both verify the source and fold its dynamic body to and i64 %x,4294967295; constant source probes fold to ret i64 0 while the prescribed-move equivalent folds to ret i64 4294967296. These probes ran headlessly through stdin/stdout. The dynamic form can survive the supported O0 envelope; it accesses no memory, encounters no UB and is not layout-dependent. The round-4 GEP fix correctly addresses index width, but does not fix this separate representation-width case. [LLVM 18 pointer conversion semantics](https://releases.llvm.org/18.1.8/docs/LangRef.html#inttoptr-to-instruction). *Fix:* In sections 1.5 and 16.2–16.4 state: "For an integral pointer in address space A, let P(A) be its datalayout representation width, falling back to the datalayout default pointer entry; pw=P(0) is the ISA address width, not the width of every LLVM pointer. inttoptr first truncates or zero-extends its integer operand to P(A); ptrtoint truncates or zero-extends the P(A)-bit pointer value to the destination integer width. Preserve these conversions in constant expressions, parameters, aggregate fields, results and pointer memory operations. GEP computes within its address space's P(A)-bit representation using I(A), preserving only representation bits above I(A). A carrier bridge to ISA addresses must preserve these source semantics; addrspacecast uses the incoming target's conversion semantics rather than an unconditional move." Apply the bridge equally in section 17.4 and the native build, keeping section 18.1 consistent. For the witness, the canonical value computation must be trunc i64 %x to i32 followed by zext i32 to i64 (or an equivalent explicit low-32-bit mask); f(4294967296)=0/code 0 and f(4294967297)=1/code 0. Add a checked dynamic source/map pair and native constant probes. Two viable implementations are (a) normalize nonzero-address-space operations into width-correct integer carriers and target conversion code before the existing map, or (b) carry P(A) explicitly throughout the mapper and bridge at ISA memory operands. I recommend (a), which retains the single-width ISA address model. Do not reject mixed-width layouts; ISA 0.8 integer truncation/extension rows already express this witness.
- **[codex] R5-CODEX-01** (§5.1–§5.3, especially PT6/PT7/PT8; §3.4 finite dispatch domains; core/S0): PT6 defines a load as "the union of AV(X, o′) over the slots o′ that overlap [o, o + size(T))" and also adds whole initializer INT atoms. Union is not byte reconstruction. Witness under datalayout "e-p:64:64": @width = internal constant [2 x i8] [i8 1, i8 1]; in @top, %w = load i16, ptr @width, align 1; %n = zext i16 %w to i64; %h = call ptr @__bennett_qalloc(i64 0, i64 %n); apply gate X twice at index 256 and qfree %h. The concrete load is 257, and the register has 257 wires, so both gates and the clean free succeed. PT6 instead unions the two INT(1) atoms, yielding VS(%w)=VS(%n)={1}; section 3.4 therefore compiles only the width-1 alternative. A compare-tree dispatch cannot handle the actual width 257, or an unconditional width-1 allocation makes the first gate trap T-INDEX. Neither implements the reference execution. I reproduced accept with atoms {INT(1)} and value set {1} in the repository recognizer. LLVM 18 and 23 verify the source, preserve its load through default<O0>, and independently fold it to qalloc(0,257) under instcombine. This contradicts section 5’s explicit claim that the runtime value is always a member of the reference set. *Fix:* In §5.1–§5.2 state: "Memory atoms carry their storage interval and representation width. A load may copy a whole-value atom only when the load covers that same interval with a compatible representation. For a partial, spanning or overlapping access whose resulting bits are not represented exactly, set the non-handle value to top; do not union component INT values as possible whole loaded values. Any partial store or copy that may affect the loaded interval must participate in this rule. ROOT provenance remains explicit, and §6.2’s partial-handle restrictions remain in force." Make this the fixed reference rule, not an optional precision improvement. For the witness, immutable-image decoding must produce INT(257), finite dispatch {257}, a 257-wire register, two successful X gates at wire 256 and a clean free, with no fault. Add a checked recognition/dispatch execution case and a second case that loads a subrange of a larger stored integer. A fully specified byte-level abstract domain is another valid repair and can retain more finite results for mutable memory; I recommend exact immutable-image decoding plus the stated conservative fallback as the smaller correction.
