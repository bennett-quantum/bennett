- **[sol] B2** (Recommended exact spec diff — §10 synchronous adapter paragraph; contract): ISA §10 Results explicitly gives a FAILED run zero values and one terminal fault record. The proposed adapter nevertheless gives a single sequence that distinguishes failure, extracts declared results, closes and returns to the native caller. It specifies neither the native failure carrier nor a default continuation. For an i32 entry that stores 7 and then executes fault 21, there is no i32 result to extract. Returning a fabricated scalar, returning a tagged failure and invoking a failure continuation produce different subsequent native behavior. Distinguishing API errors from device faults is necessary but does not decide that behavior; deferring numeric encodings cannot settle it. *Fix:* Replace that §10 paragraph with: 'On COMPLETED, extract the declared values, close, and return success. On FAILED, extract no ordinary values; preserve the exact terminal 64-bit fault code, close under the stated prefix-commit rule, and deliver DEVICE_FAULT(code). API failures deliver API_ERROR(status) and MUST NOT be substituted for device faults or implicitly close an active run. The companion API's default outcome is a tagged success/device-fault/API-error result. An adapter preserving a native signature without a failure carrier MUST bind an explicit failure continuation in its descriptor and invoke it instead of performing a normal native return on failure.' An explicit status-returning native convention is the other viable route; prefer the tagged companion plus bound continuation for unchanged source signatures. Specify the example: entry byte 3, store 7, fault 21 yields DEVICE_FAULT(21), no scalar value, and byte 7 after unreversed close; eligible reverse before close restores byte 3.

## sol

The cited launch/memory defect is real, and the cited clause numbers are accurate. The proposed ownership and coherent-memory rules are sound in outline, and the 0.10 publication route is correct. Two contract issues prevent application: scalar entries can omit shared-global bindings, and native failure returns remain undecided. Core scope is acceptable.

**Path to accept:** First add mandatory implicit-global binding and per-invocation synchronization, with all three P0 observation rows as conformance obligations. Then replace the synchronous return rule with explicit success/device-fault/API-error delivery and a defined native failure continuation. Retain the proposed ISA 0.10 companion-contract route; backend implementation and complete numeric wire layouts are not required for this proposal's acceptance.

- **C1 4**: The proposed registration, generation, epoch and lease records fit §§3.2, 7.4 and 10. Ownership through CLOSED and reversal to the invocation's entry state are coherent. *Change:* In §10 add: 'Each invocation records its complete shared-storage binding set, including implicit global bindings, before executing its first device instruction.'
- **C2 5**: No instruction is added or incorrectly redefined. The distinction between pointer bits and native access authority is compatible with §4.1's numeric ptrtoint/inttoptr operations. *Change:* No instruction-set change is required.
- **C3 5**: Private coherent import, prohibition of native RAM reads at quantum addresses, and retention of prefix reversal preserve §§5.2, 7.2 and 14.2. Registration does not purport to expose coherent state as native bytes. *Change:* No coherent-semantics change is required.
- **C4 4**: The proposal preserves device budgets and existing allocation semantics, but does not explicitly delimit registration and transfer accounting. *Change:* In §10 state: 'Replay and transfer instructions included in the materialised device body consume their ordinary reference steps and resources; native registration, lease and marshalling overhead is reported separately with an explicit scope.'
- **C5 3**: The registration obligations are substantial, and deferring numeric C encodings is reasonable. However, the exact diff does not require implicit shared-global bindings for scalar entries, and its synchronous return rule lacks a defined failure carrier. *Change:* In §10 state: 'The mixed profile applies whenever the selected device closure accesses native-shared storage, including globals absent from the entry's parameter list; such globals MUST have common native/device bindings across every participating entry.'
- **C6 4**: The extracted memory_and_ownership and closure_inventory_and_modes checks pass, but are correctly labelled finite models. ref_catalog.py --check also passes: 219 recipes, envelope hash 5de4e4995350313e50217880ba1b95de39cd043283b726337d4894efb005d197. No native-sharing backend execution was established. *Change:* Add to the conformance obligations: 'Starting with native g=0, the three launch-global-state scenarios MUST produce respectively 1 2 host_global=2, 1 41 host_global=41, and 1 2 host_global=2, through generated native adapters.'
- **C7 4**: The mixed-object section preserves native main, host-only libc, selected device closures and per-root certificate contexts. The ISA 0.10 route is appropriate. The unresolved scalar-global case nevertheless leaves the stated P0 consumer outside the bridge's mandatory coverage. *Change:* In §10 state: 'Mixed native/device sharing includes storage reached through global references, independently of whether a call carries pointer or aggregate arguments; neither private per-entry global copies nor compulsory promotion of native main implements that sharing.'
- **C8 3**: The note is clear about implementation limits and publication ownership. Implementers still need semantic decisions about global binding and native failure continuation, beyond merely filling in wire layouts. *Change:* Replace the synchronous-adapter paragraph with the explicit success, device-fault and API-error branches specified in B2.

Suggestions:
1. In 'Hashes, catalog and consumers' add: 'Publishing ISA 0.10 changes the version-prefixed symbol envelopes even when function bodies are unchanged; regenerate affected interface/closure identities, program-point references, schedules, certificates and consumer pins. The existing ref@0.9 catalog retains its published bytes/hash. Any 0.10 catalog binding or compatibility with ref@0.9 is published explicitly.' The claim that this proposal need not edit existing recipe bodies is correct; it does not imply unchanged 0.10 envelopes.
2. In §10's private-oracle paragraph add: 'Import MUST use a published realization consistent with the reference initial state and budget. Existing materialised snapshot/replay remains the default where applicable. A profile changing the initial allocator state directly MUST specify corresponding amendments to §§3.7, 5.2, 11.1 and 14.1; it MUST NOT supply different construction-state records under an unchanged ref@0.9 binding.' This makes the existing soundness obligation easier to implement without demanding a new proof format.
3. In 'Mixed fat object' replace the ledger wording with: 'Each root has its own certificate binding and root-relative context; register and token namespaces belong to the loaded program/run under §§3.3, 5.4 and 10. Roots in one loaded program share that program's ledger; distinct programs require explicit routing or transfer.' This avoids reading 'each root keeps its own ... ledger' as mandatory ledger separation.
4. In §10 clarify: 'Pointer/integer conversions may resolve an existing authorized registration under the selected mapping profile; they never create one. Defined address observations and round trips remain preserved.' Numeric conversion and allocation authority are separate concerns, consistent with the [LLVM 18 pointer aliasing rules](https://releases.llvm.org/18.1.8/docs/LangRef.html#pointer-aliasing-rules) and [inttoptr semantics](https://releases.llvm.org/18.1.8/docs/LangRef.html#inttoptr-to-instruction).

## codex

The boundary defect is real, the cited premises are accurate, and ISA 0.10 is the correct publication route. The core constructions remain sound. Revise the contract to bind implicit shared globals explicitly: pointer-argument registration alone does not resolve the live scalar-counter blocker.

**Path to accept:** Add the mandatory implicit-global binding and authoritative native-state rules in NS1, then include the three exact consumer observation rows as conformance requirements. Numeric wire layouts and an implemented backend are not required for this proposal vote; their publication remains a prerequisite for consumer implementation.

- **C1 4**: The proposed leases, entry epochs, retained FAILED prefixes and close semantics fit ISA §§7.4/10. Imported oracle state needs a clearer connection to the fixed initialization in §3.7. *Change:* In §10's coherent-import paragraph, state: 'The default coherent import supplies preserved interface inputs and materialised replay rows; it does not override §3.7's initial machine state.'
- **C2 5**: The amendment adds no opcode or incompatible launch-0.9 argument tag. Its rejection of unchecked native-pointer casts is justified by §§4.1/7.1/10. *Change:* No score increase is available. Clarify §10: 'Registration capabilities are adapter values; after checked marshalling, ISA ptr values and ptrtoint/inttoptr retain their §§3.3/4.1 semantics. Integer conversion does not create a registration.'
- **C3 4**: Private coherent memory, no quantum-addressed native RAM reads, retained measurement/free restrictions and invocation-local reversal preserve the existing sound constructions. The import's position relative to reference execution should be explicit. *Change:* Add to §10: 'The imported image, mapping and metadata remain fixed throughout each coherent forward/inverse pair; replay is reversed before its preserved inputs are released, and private oracle writes are not published as native memory mutations.'
- **C4 4**: The proposal preserves device-private allocation semantics and names budgets in escaping-allocation profiles. It does not explicitly allocate import, preparation and shim costs between existing accounting domains. *Change:* Add to §10: 'Host capture, registration and shim costs are reported separately; executed CC transfer instructions and quantum preparation, replay and cleanup retain their existing resource charges, and every replay row in the oracle reference body consumes one step of B.'
- **C5 3**: The missing §10 pointer/aggregate binding is accurately identified, and the versioned companion route is appropriate. However, the proposed descriptor does not require binding implicit shared globals, so it does not yet answer bp-acm's zero-argument counter example. *Change:* Require in §10: 'Every native-call descriptor binds the selected device closure's boundary-shared globals to their resolved native storage, including entries with no pointer or aggregate arguments; all entries referencing the same native definition use one canonical registration.'
- **C6 4**: The bookkeeping witnesses pass when rerun and are correctly labelled as models rather than backend execution. A read-only interpreter check also confirmed the distinction between changing a global image and adding charged replay rows. The three consumer observations are absent from the proposal's explicit acceptance vectors. *Change:* Add the consumer's three normative rows to 'Conformance vectors': repeated top calls produce '1 2 host_global=2'; an intervening g=40 produces '1 41 host_global=41'; top followed by another entry sharing g produces '1 2 host_global=2'.
- **C7 4**: The note explicitly preserves native main, host-only libc, selected device closures, per-root certificates and coordination across roots. It passes the architectural mixed-object scoping check, but the shared-global omission prevents the concrete native-sharing promise from being complete. *Change:* Replace §0.3's ISA-11 classification with: 'Promotion retains the all-device construction; retaining pointer-sharing native callers requires the negotiated §10 mixed-memory contract and is a boundary capability obligation, not merely an efficiency improvement.'
- **C8 4**: The note clearly distinguishes proposal, publication and implementation, and its cited VM proposal and eleven future vectors exist. Deferring numeric encodings to the companion publication is appropriate; the shared-global association remains a semantic decision rather than a wire-layout detail. *Change:* In 'K entry: 0.9 versus 0.10', state: 'Publish the companion's descriptor, operations, default profile and status behavior together with the ISA 0.10 reference; consumers negotiate that exact publication before creating registrations or runs.'
